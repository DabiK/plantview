# PlantView — suivi de la boucle Ralph

## Objectif

App React de visualisation PlantUML 100 % client : liens encodés `/view/<code>`, éditeur minimal `/edit`, aucun backend, aucun serveur PlantUML distant.

## Règles

- Une seule tâche par itération (issue GitHub = tâche). Ne jamais commencer la suivante dans la même itération.
- `pnpm lint && pnpm typecheck && pnpm test && pnpm build` verts avant commit (plus `pnpm test:e2e` à partir de M7).
- Commits atomiques, jamais de build cassé. Rendu local uniquement (aucun appel à plantuml.com/planttext/kroki).
- Mettre à jour ce fichier + cocher `PRD.md` + fermer l'issue GitHub (`gh issue close <n>`) à chaque tâche terminée.

### M3 — Rendu PlantUML local (@plantuml/core) lazy + sanitize — DONE

- `scripts/sync-plantuml-assets.mjs` : copie `plantuml.js`, `viz-global.js`, `emoji.js`, `openiconic.js`, `themes.js` de `node_modules/@plantuml/core/` vers `public/plantuml/` (créé au besoin, exit 1 si le package est absent). `"postinstall"` ajouté dans `package.json`, vérifié via `pnpm install --frozen-lockfile` (le lockfile ne bouge pas).
- `src/lib/render-plantuml.ts` :
  - `renderPlantUml(source, { dark })` → SVG sanitizé. Chargement unique de `viz-global.js` par balise `<script>` classique (singleton, rejet propre + retry possible après échec), puis import dynamique du moteur. `window.PLANTUML_STDLIB_BASE = <base>/plantuml/` pour que themes/emoji/openiconic se chargent depuis nos assets.
  - Les rendus sont **sérialisés par une queue de promesses** : le moteur TeaVM partage son état interne (doc GITHUB_INTEGRATION.md). Garde « latest request » par `requestId` : une requête périmée rejette avec `PlantUmlRenderError` et `superseded: true` (le caller ignore).
  - `parsePlantUmlError(raw)` : extrait `Error line (\d+)` (→ `line`, sinon `null`) et garde la 1re ligne utile comme message court ; fallback « Unknown PlantUML error. ».
  - Sanitize DOMPurify `USE_PROFILES: { svg: true, svgFilters: true }` ; vérifié en navigateur : `xmlns` et `viewBox` conservés.
  - Aucun import statique de `@plantuml/core` (grep sur `src/` vide) ; le moteur n'est pas dans le bundle.
- **Piège Vite 7 résolu** : `import(/* @vite-ignore */ '/plantuml/plantuml.js')` est réécrit en `__vite__injectQuery(url, 'import')` → `?import` sur un fichier de `public/` = 500 « This file is in /public … should not be imported from source code ». `@vite-ignore` ne l'empêche pas. Solution : construire une **URL absolue** via `new URL(`${import.meta.env.BASE_URL}plantuml/plantuml.js`, window.location.href)` ; `injectQuery` ne touche pas les URLs `http(s)://`. Testé en dev **et** en `pnpm preview`.
- **Constat moteur (important pour M5)** : les erreurs de syntaxe ne passent pas par `onError` — le moteur résout un SVG contenant le texte d'erreur (`Syntax Error? (line N)`, « Diagram not supported… »). `onError` ne semble servir qu'aux échecs sévères. M5 devra détecter ces SVG d'erreur (heuristique texte/style) pour afficher le panneau stylé ; `parsePlantUmlError` reste utile si `onError` se déclenche.
- QA navigateur (chrome-devtools, dev puis preview) :
  - `@startuml\nBob -> Alice: Hello!\n@enduml` → SVG avec `<title>Bob</title>`, « Alice », `xmlns`, `viewBox`, ~650 ms après warm-up.
  - `{ dark: true }` → SVG différent du rendu clair.
  - Deux rendus lancés coup sur coup : le 1er rejette `PlantUmlRenderError { superseded: true }`, le 2e (C→D) aboutit.
  - Zéro message console de niveau erreur/warn (le moteur log beaucoup en `console.log`, c'est normal).
  - `dist/plantuml/{plantuml.js,viz-global.js,…}` présents après build ; `dist/assets/*.js` = 261 Ko (< 1 Mo). Le module `render-plantuml` est tree-shaké pour l'instant (aucune route ne l'importe encore) : normal, M4 le branchera.
